# Project growth patterns

Status: working hypotheses distilled from Anders's current projects. Apply the
pressure and transition, not the example's filenames or tools.

| Start with | Pressure that earns more structure | Add |
|---|---|---|
| One short root router | Independent areas need different rules or reading sets | Nested routers with bounded branches |
| One current note or inline next step | Work spans sessions or settled actions keep reopening | One authoritative action list or work register |
| Git history | A surprising, expensive, or hard-to-reverse choice will matter later | A decision note or ADR |
| URLs, dates, and plain provenance | Sources are repeatedly transformed, compared, audited, or must be reconstructed | Separate original evidence, faithful derivation, and interpretation |
| A manual method | Repetition, precision, or consequential effects make variation costly | A script, test, or application that owns the deterministic behavior |
| One current-state owner | External state changes faster than durable intent | A dated state snapshot separated from goals and doctrine |
| One root map | Agents must load unrelated context to find the relevant branch | Selective routing or generated views |
| A clean personal `main` workflow | Concurrent work or team governance makes direct synchronization unsafe | The repository's branch, review, and publication workflow |

Some distinctions recur without requiring the same structure:

- Lived-practice projects may separate dated outcomes from reusable methods.
  The outcome can correct what the method recommends next.
- Operational projects may separate durable intent, volatile state, current
  actions, and evidence.
- Evidence-heavy projects may separate original material, faithful
  transformation, and interpretation. Bronze, Silver, and Gold are one local
  vocabulary, not the rule itself.
- Executable projects let code, configuration, tests, and owning present-tense
  docs define current behavior.
- Large collaborative projects may need planning and execution systems that
  would be monitoring burden in a small personal repository.

Current evidence comes from Cooking, Training, MIT, Hub, Seatankers, and Odin.
Their useful shared lesson is one owner per question and structure earned by
use. Their folder names, Obsidian conventions, source tiers, trackers, direct
push rules, and operating machinery remain project-specific until broader use
earns otherwise.
